# Changelog

Per-version history of the app. The snapshot of what exists now is [[current-project]] (`docs/current-project.md`); this file explains how each part got there, version by version, including the tests and what was **not** clicked through in a real browser.

**Do not read this file whole** (about 45k tokens). Search it for a version number (`v1.147.0`) or a feature name instead.

**Adding an entry:** put one entry for each code change at the top of the first section below, newest first. It names the version, what changed, the tests, and what was not checked. `docs/current-project.md` changes only when the snapshot changes (workflow, modules, limitations, open work).

On 2026-11-04 the two sections below were moved here word for word from `docs/current-project.md`, where they had grown to about 80% of the file. Only their headings were changed (from `###` to `##`, with the range of versions added). The first section is still named for its oldest entries; it holds entries on every area from v1.25.0 to v1.157.0.

## Cameras and tags (entries v1.25.0 to v1.160.0)

- **The confusion matrix moves to the top of the options panel, for ResNet50 only (v1.160.0).** v1.159.0 had made Insights a view of the step-2 Classifier; now the matrix is the **first region of the right-hand pane** (`PanelSection` "Confusion matrix", `ClassifyView.matrixPanel`, shown above the Grid controls and above whatever Scatter and Outliers add through `PanelPortal`), in every view, and the *▥ Insights* button and the `insights` mode are gone. **Only ResNet50** (`classify_view.MATRIX_METHOD`): `GET /insights` reports `methods` as `["resnet50"]` when it is switched on and the new reason `method_off` when it is not, and the Show entries of the cells exist for that method alone (the CPU and R18 entries are gone; `classify_api._matrix_methods`). Several methods or computations are left for later (noted in the project memory). The region is compact for the 300 px pane (`says OK` / `labeled OK` headings, accuracy line under the table, the info tip explains the positive class). It is read again whenever the page's `revision` changes, which includes the end of **Refresh scores** (the job bumps it) and every label or golden change; **greyed out with a note** (`data-outdated`) while `st.stale.goldens`, `st.stale.frames` or a missing ResNet50 score says the scores are older than the goldens or the pictures (a label alone does not make the leanings stale: they depend on the goldens only). Where it cannot be calculated the region says what is missing instead of staying empty: `method_off`, goldens in one class only, no test pictures, no scores yet. A cell still turns the Grid to its Show entry (and leaves a Scatter or Outliers view for the Grid). Only a step-2 Classifier has the region. Tests: frontend (the region is first in the pane above the Grid controls, a cell sets Show and the grid request, the region stays first in Scatter and Outliers and a click there goes to the Grid, greyed out when stale, read again after Refresh scores, absent in step 1, the hints for missing goldens and ResNet50 off); backend (ResNet50 only and `method_off`, the Show entries absent when it is off; the cell tests run the matrix on the classical method through `mock.patch.object(cv, "MATRIX_METHOD", "cpu")` because the test machine has no torch); full suites: 927 frontend, 1074 backend (5 skipped), `tsc --noEmit` clean. **Not clicked through in a real browser**, and not run with real ResNet50 scores.

- **Insights moves into the Classifier: a view of Classify, its cells are Show entries of the one Grid (v1.159.0).** The Insights page (menu item, `/insights` route, `InsightsView`, its own card list) is gone. A **step-2 Classifier** has a fourth view, **▥ Insights**, next to Grid, Scatter and Outliers (`classify/ClassifyInsights.tsx`; the button and the view only when `st.step === 2`, a Classifier that leaves step 2 falls back to the Grid; the Refresh scores line shows in Insights too). It shows one confusion matrix per method in use (the API already returned one per active method: `methods_available()` is the set switched on in Configuration), rows = your label, columns = the method's leaning, goldens left out; new: **pictures muted in this Classifier are left out too**, so the matrix describes the pictures the Classifier shows. A number is a button that turns the Grid to that cell: `classify_view.matrix_view_name` / `matrix_lookup` make one **Show entry per cell and method**, offered by `valid_views(..., matrix_methods=...)` for a step-2 Classifier only (`classify_api._matrix_methods`; in step 1 the entries are not offered and a request for one answers 422), and `filter_and_sort(..., matrix_cells=...)` keeps the labeled non-golden pictures of that cell with the same rule as the count (`insights.cell_frames`). The Show box therefore names the open cell and everything of the Grid works inside it: *Order by* (also *Worst fit first*), paging, the keys, the picture viewer and the coloured borders of step 2. **Names:** OK is the positive class, as the user defined it: labeled OK and model OK = true positive, labeled OK and model NG = false negative, labeled NG and model NG = true negative, labeled NG and model OK = false positive; each entry carries the plain meaning in brackets, `R50 \u00b7 False negative (labeled OK, model says NG)`, so the words cannot mislead; for classes other than a OK / NG pair the entry is `R50 \u00b7 A \u2192 leans B`. Removed: `GET /insights/cell` (answers 404) and `api.insightsCell`; the Insights icon and menu entry; `tools_used.py` still knows the `insights` tool name, so labels already stamped `via="Insights"` still count, but nothing stamps it any more. Tests: backend (classify_view: names, per-method offer, a cell's pictures without goldens; API: the cell names and the grid lists exactly the cell's frames, 422 in step 1, a wrong label appears as a false negative, muted pictures leave the matrix, `/insights/cell` is gone) and frontend (matrix per method, a cell turns the Grid and the Show box names it, no Insights button in step 1, the missing-goldens message, menu and tool-icon tests without Insights); the full backend suite (1073 passed, 5 skipped) and frontend suite (923) pass, `tsc --noEmit` clean. **Not clicked through in a real browser.** Not done: storing the matrix with a frozen version, and a cell filter for the old per-method "Methods disagree" view.

- **New Classify order: Worst fit first (v1.158.0).** Grid *Order by* gains *Worst fit first* (`classify_view.WORST_FIT_ORDER`, offered through `cv.ORDERS`, so the API and the page need no other change; no frontend rebuild). The sort key is the bar of the picture's own label under the *Rank using* method: `nearest class distance / the label's distance` (the same number the card's bars show, `bars()`), lowest first, so the pictures whose label the method places farthest from its nearest class come first (the user's example: both NG, OK 100%, NG 85% before NG 95%) and a picture the method agrees with (100%) comes late. Ties (all the agreeing ones are at 100%): the larger distance to the label's own goldens first, then the name. Pictures with no label, no distance to the label's class, or that are goldens themselves (no scores) go last, by name. A zero distance counts as 100%, as in `bars()`. It orders; it does not filter (the *Disagrees with label* view hides pictures, this does not), so it combines with any Show. It works in step 1 and step 2 alike. Use: in a step-2 Classifier, the labeled pictures at the top are the ones the goldens do not yet teach the model. Tests: 4 in `test_classify_view.py` (the lowest label bar first, the user's 95% / 85% example, ties and unlabeled last, a missing distance and a zero distance); that file passes (15 tests). The rest of the backend suite and the API could not run in the build session (no web framework installed there); the API only checks the name against `cv.ORDERS`. **Not clicked through in a real browser.**

- **The picture viewer fetches a whole grid page ahead, not just the neighbours (v1.157.15).** v1.157.14 preloaded two pictures ahead and one behind; browsing fast outran that. `FrameViewer` now hands `FramePane` every picture of the viewer's list, nearest first with the one ahead before the one behind (at most 160, `DEFAULT_MAX_ENTRIES`: a 128-picture page is covered whole from any position). `pictureCache.prefetch(urls)` replaces `warm`: it fetches at most 3 at a time (the server renders each one, crop and filters), takes the list as a priority order, and a new list (the viewer moved) drops what has not started while requests under way finish and stay cached; a picture asked for with `load` while queued is fetched once; a 404 (a cut-out with no found box) is remembered and not asked for again; the cache holds up to 160 pictures, the ones just wanted counting as the freshest and the one on screen never freed; only the four nearest are decoded ahead (decoding a page would only hold memory); `dispose` stops the queue. The hold logic itself is off where the browser has no `Image.decode` (the test DOM), which then shows the wanted picture at once as before v1.157.14: the one-render lag of the swap made four `FrameViewer` tests intermittent (a Picture edits-fed ROI, a Dedup box cut-out), found by repeating the file 15 times; after the change 12 repeats of the three viewer test files passed. Tests: `pictureCache.test.ts` (three at a time and nearest first, never twice, a new list drops the queued ones, a 404 not retried, `dispose` stops the queue), `FramePaneHold.test.tsx`; full frontend suite and `tsc --noEmit` run before the patch. **Memory:** every cached picture is held as its bytes (PNG, full size of the cut-out), so 160 pictures of a large cut-out can take a few hundred MB of the browser; the size was not measured on real cameras. **Not measured on real data, not clicked through in a real browser.** The first picture after opening, and a jump past the fetched part, still wait for the server.

- **Browsing in the picture viewer no longer flickers: the old picture stays until the next is ready, and the neighbours are fetched ahead (v1.157.14).** Moving from one picture to the next in the viewer overlay (Classify grid, and every viewer built on `FramePane`) showed an empty gap. Causes: `FramePane` gave the `<img>` `key={frame}`, so each step created a new element that was blank until its picture arrived; and for a picture the server renders on request (a Picture edits cut-out with a crop and filters, a detector cut-out) the arrival takes the full render and a full-size PNG, sent with `no-cache` and no validator, so nothing was ever reused. Now `FramePane` keeps the picture on screen and loads the wanted one off screen, decodes it (`Image.decode()`), and only then swaps (the size and the "loaded" frame change in the same step, so the zoom and the fix point behave as before). `FrameViewer` passes `preload`: the pictures two ahead and one behind, in the form the pane would show them (frame, Picture edits output with or without the filters, detector cut-out, Dedup-box picture). With `preload` the pane fetches each into a blob once (`pictureCache.ts`, 12 entries, the one on screen never freed, all freed when the pane goes away), so a preloaded picture is shown with no request and no decode wait; without `preload` (the other users of `FramePane`) it loads the plain way but still holds the old picture. A picture that cannot be had (404, a cut-out with no found box) falls back to the usual `src`. Where the browser has no `Image.decode` (the test DOM) the swap is at once and nothing is preloaded. Overlays (outline, found box) are computed for the picture the viewer wants, so for the moment between the key press and the swap they may sit on the old picture. Tests: `pictureCache.test.ts` (fetched once, a failed fetch not kept, the limit never frees the shown one, `warm` never rejects) and `FramePaneHold.test.tsx` (the old picture stays while the next is on its way, a neighbour is fetched once and shown from the preload, a 404 is shown the usual way); full frontend suite 919 passed, `tsc --noEmit` clean. **Not measured:** the real gain on a camera with a crop and three filters (the server render per picture is unchanged and still runs once per picture, now ahead of time), and **not clicked through in a real browser**. Not done: a server-side cache of rendered pictures, and a lighter format than full-size PNG; both need the render time measured first.

Names are the Chain names. At most 500 pictures are listed, the count is the whole number. The page of a step-1 Export (Freeze) has a card **Pictures in neither OK nor NG** with the button **Show them** (not loaded until asked for, and dropped when the lines change): the reasons table, then a card per picture with its thumbnail. The step-2 Export has none. A picture labeled by every Classifier is never listed (it is OK or NG), so every listed picture has at least one Classifier with no label for it. Tests: 3 backend (no lines, unlabeled, absent), 2 frontend. Not checked in a real browser, nor against real chains with Picture edits and Dedup boxes in front of Classifiers (the walk up was tested for the Classifier's own mute only); two-line check: open Freeze 1, press Show them, compare the count and the reasons with 42 pictures and Dedup 5 / foam-4. - **A line dragged onto a box lights its input dot anywhere on the box (v1.157.2).** Dragging a detector's output onto another detector showed no green dot except right at the small input dot, and the reverse drag showed red almost everywhere. Reproduced in headless Chrome with a grid of drag positions over a synthetic camera. Causes: (a) React Flow picks the nearest dot of either kind within the 40 px radius, so the output dot beside the input dot won and a strict-mode check rejected it; (b) there was no drop target on the box body; (c) a dot without an id resolves to the first dot of its kind in the DOM, which for a detector was the first target dot (`t:...`), so the wrong dot lit and the line left from the wrong place (older fault). Fix in `ChainView.tsx` / `styles.css`: the main output dot is now first in the DOM; `BodyDropZones` adds an invisible whole-box target (and source, for the reverse drag) that is never a place to start a line. After the fix the forward drag is green over the whole body, the reverse drag green over most of it (red only on the dots' own enlarged hit areas and the left-edge strip), and real drops create the lines. Tests: new in `ChainView.test.tsx` (dot order, drop zones, none on Classifier or Ingest input); the dot count in `ChainSteps.test.tsx` ignores the drop zone. Not checked: the user's real camera and Windows Chrome.
- **A detector target takes 12 examples instead of 6 (v1.157.1).** `flow.MAX_EXAMPLES` went from 6 to 12 (the limit had no stated reason; no frontend limit exists, the panel only counts them). The detector searches every picture once per example of a target and keeps the best match, so the run time grows in a straight line with the number of examples: measured once on a synthetic 640 x 480 picture on the Linux dev machine, one search took about 194 ms with the full turn range and about 34 ms with a turn of at most 10 degrees either way, so a target with 12 examples costs about twice what 6 cost; not measured on the laptop or on real pictures.
